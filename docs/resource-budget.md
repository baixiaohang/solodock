# SoloDock resource budget

> English (authoritative) · [简体中文](zh-CN/resource-budget.md)

This document records budgets, measurement methods, and measured baselines. See [testing and safety guardrails](testing.md) for feature-level isolation scenarios and destructive-test rules.

The resource harness is [`scripts/measure-resources.sh`](../scripts/measure-resources.sh). It runs the `embed-ui` release binary with private temporary state/config and an exact PID, emits JSON, and terminates only that invocation on failure. Shared CI runners use a broad 512 MiB idle-RSS ceiling only to catch regressions; it is not a real 2-vCPU/4-GiB target-host measurement.

Targets are 40–100 MiB idle RSS, normally below 1% idle CPU, 10–40 MiB RSS growth under representative StreamGate load, and a transient 100–300 MiB SoloDock footprint during pull/Compose. Docker-daemon decompression/image memory must be reported separately. The binary, UI, and control-plane metadata should remain tens of MiB; metadata excludes image layers and business data and must stay below 100 MiB.

Webhook ingress is fixed at a 1 KiB body, 16 concurrent requests, bounded global/per-application rate buckets, and one coalesced wake sequence per application. Resource acceptance retains the control-plane/DinD ceilings and verifies that replay rows, rate maps, and inflight permits fall after a burst instead of turning notifications into an in-memory queue.

Every formal acceptance run records kernel, CPU/memory cgroup limits, Rust/Node versions, commit, warm-up/sample windows, binary size, RSS/CPU/FD/tasks, Docker-daemon peak, and whether DinD was used. Weekly Monday and manual `Extended CI` runs produce three formal machine-readable reports. `resource-report.json` runs the production embedded binary with a 60-second warm-up and 60-second idle CPU sample. `docker-e2e-resource-report.json` keeps 8 authenticated SSE connections (4 events, 2 logs, 2 stats) for 60 seconds during complete private-Registry/DinD auto-deploy, health-failure recovery, manual rollback, and data-canary scenarios, then records stream growth, control-plane peak, and metadata size at the end of the window. `docker-daemon-resource-report.json` locates `dockerd` by process name inside the outer isolated DinD container and samples its `/proc/<pid>/status` for a separate daemon RSS peak. JSON records `stream_hold_seconds` and sample timing explicitly. Ordinary PR/package artifacts use a 1-second warm-up, 5-second idle sample, and 1-second SSE hold only for fast liveness, broad RSS ceiling, and StreamGate-release checks; they are not formal baselines. All remain local/CI measurements rather than target-production measurements. Do not set a `MemoryMax` that could kill the process during recovery.

## Local baselines

On 2026-08-29, Linux 6.6 WSL2 and Node 24.12 at baseline `b360d01e` simulated 2 vCPU / 4 GiB with cgroup `cpu.max=200000 100000` and `memory.max=4294967296`. After 60 seconds of warm-up and a 60-second production embedded-binary sample: RSS was 13,440 KiB, CPU 0.0167%, with 16 FDs, 5 tasks, and a 20,697,056-byte binary. In the isolated Registry+DinD formal 60-second stream scenario, in-process control-plane idle RSS was 26,084 KiB; 8 streams measured 29,028 KiB at the end of the window (2,944 KiB increase), with a 30,124 KiB peak and 2,434,439 bytes of metadata. Separate `dockerd` peak RSS was 80,688 KiB. A complete DinD 5/5 run on the same final code also passed. CI artifacts recheck the final commit. The test process includes the HTTP harness, making this a conservative regression baseline rather than exact production-binary residency.

On 2026-08-30, the same WSL2 toolchain ran the production embedded binary in the M6 worktree based on `03206a4b` for 60 seconds of warm-up plus a 60-second idle sample: RSS was 13,824 KiB, CPU 0.0000%, with 16 FDs, 15 tasks, and a 21,079,176-byte binary. The isolated Registry+DinD formal 60-second window held 8 authenticated SSE connections while traversing signed webhook, durable wake, private-Registry polling, and existing deployment/rollback flows: control-plane idle RSS was 29,248 KiB, end-of-window RSS 30,528 KiB (1,280 KiB increase), peak 31,152 KiB, and metadata 2,546,541 bytes. Focused tests verified nonce-replay TTL/batch cleanup, one sequence per application, and limits of 16 permits, 120 global, and 10 per application. CI artifacts continue to verify final-commit numbers. This host did not apply a 2-vCPU/4-GiB cgroup ceiling, so these values are a broad regression baseline only.

Together, the reports exercise idle, streams, deployment/rollback, and bounded metadata, but they are not measurements from the target production host and do not mix Docker peak memory into SoloDock RSS. Re-run the same workload during the target host's maintenance window. `MemoryHigh=256M` is a soft-pressure signal, not a kill limit; adjust it only if target-host steady state or peaks materially exceed CI baselines.
